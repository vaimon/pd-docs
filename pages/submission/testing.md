# Тестирование и совместимость

Первыми проект должны проверить вы сами, а не жюри. Сборка, работающая только из рабочей папки разработчика, может не запуститься после скачивания или на другом устройстве. Команда отвечает за то, чтобы сданная версия работала всё время, пока идёт проверка.

## Проверка глазами нового пользователя

Рекомендуем попросить человека вне команды выполнить следующие действия без устных подсказок:

1. Открыть README.
2. Скачать сборку либо перейти на сайт.
3. Установить только те зависимости, которые указаны в инструкции.
4. Выполнить основной сценарий.
5. Завершить работу и открыть приложение повторно.

Запишите места, в которых понадобилась помощь. Это те места, где не хватает инструкции или подсказки в самом приложении.

Тестировщики оформляют найденные ошибки в issues. В карточке ошибки полезны шаги, ожидаемый результат, фактический результат, версия приложения и устройство. Подробный пример есть в [разделе об обратной связи](../results/feedback.md).

## Доступ для проверяющих

Для проверки нужны публичная сборка или ссылка и доступ к необходимым данным и сервисам. Тестовый сценарий не должен зависеть от того, что тимлид вошёл в свой аккаунт.

Рекомендуем проверять ссылки в другом браузере или приватном окне. Если есть вход в приложение, объясните способ получения тестового доступа. Не публикуйте настоящие секреты и личные данные: используйте подготовленные демонстрационные данные.

Зависимости от сторонних API и хостинга учитывайте заранее. Если внешний источник перестал работать, команда ищет решение; не рассчитывайте, что проверяющий восстановит его вместо вас.

## Платформы и зависимости

Опишите в README поддерживаемые ОС и устройства, а также необходимые компоненты с версиями. Для десктопного приложения это могут быть компоненты .NET или другие среды выполнения.

Проверяйте разные размеры окон и экранов. Важно, чтобы кнопки оставались доступны, текст не обрезался, а основной сценарий не требовал устройства тимлида.

### Мобильные проекты

Проверьте приложение на разных устройствах; при необходимости используйте эмуляторы и инструменты разработчика.

Для Android команда отвечает за работу на версиях, разрешённых конфигурацией приложения. Если версия не поддерживается, не заявляйте возможность запуска на ней. Проверяйте и совместимость сборки с архитектурой устройства, а не только номер ОС.

Требования курса предусматривают поддержку 32- и 64-битной ARM: `armeabi-v7a` и `arm64-v8a`. Поддержка `x86` и `x86_64` будет дополнительной возможностью. Рекомендуемый ориентир — Android 8 и новее; конкретный диапазон укажите в README и проверьте.

Для iOS рекомендуется поддерживать текущую мажорную версию и предыдущую. Заранее обеспечьте возможность проверки на выбранных устройствах. В README укажите конкретный перечень проверенных версий, а не только слово «актуальная».

### Десктопные приложения

Укажите поддерживаемую ОС и архитектуру. Для проекта под Windows ориентируйтесь на проверку в Windows 10 и 11; поддержка более старых версий не требуется. Успешный запуск на одной 64-битной Windows 11 не доказывает работу на любой другой системе.

Проверьте установку и запуск на другом компьютере, а также изменение размера окна. Не требуйте от проверяющего догадаться, какую отсутствующую библиотеку нужно установить.

### Веб-проекты

Проверьте интерфейс в разных размерах окна и доступность сервера извне. Полезно проверить обновление страницы, пустые результаты, недоступность сети и повторный вход, если он есть в сценарии.

После сдачи **не обновляйте проверяемый деплой**: он относится к сданной версии. См. [запрет подмены](release.md).

## Как упростить проверку игры

Проверяющий должен познакомиться с основными механиками примерно за **10–15 минут**, а не проходить всю игру. Предусмотрите читы, режим бога или другие возможности, облегчающие проверку, и опишите их.

Для нулевой версии отдельный ориентир — **5–10 минут осмысленного геймплея** на ключевой механике. Не путайте длительность игрового материала со временем устного доклада.

## Если проект перестал работать

Сообщите организатору и проверяющим, какая версия недоступна, с какого времени и как проявляется проблема. Сданный релиз или деплой самостоятельно не заменяйте.

Если проект не удалось запустить, проверяющий повторит попытку позже. За две неудачные попытки проверки подряд предусмотрен штраф. Время повторной проверки сообщает организатор. Работоспособность требуется в течение всей проверки — не планируйте завершение разработки к повторной попытке.
