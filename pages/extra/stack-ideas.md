# Как выбрать технологии

Стек — набор технологий, из которых состоит проект. Выбирайте его под задачу, знания команды и возможность довести приложение до работающей сданной версии.

Перечень технологий сам по себе не делает проект сложнее или качественнее. Если для игры достаточно одного движка, не нужно добавлять сервер и базу данных только ради длинного списка.

## Из каких частей состоит проект

Ответьте на несколько вопросов:

1. Где пользователь будет работать: в браузере, на телефоне, на компьютере?
2. Нужен ли сервер или проект может работать локально?
3. Какие данные нужно сохранять и кто ими пользуется?
4. Требуются ли сторонние API или оборудование?
5. Где и как жюри сможет проверить результат?

После этого перечислите части системы и выберите технологии для каждой.

Пример описания веб-проекта: «Интерфейс показывает карту и поиск; сервер обрабатывает запросы; база данных хранит аудитории и переходы». Такой разбор помогает выбрать стек осмысленно.

## С чего можно начать

Ниже — отправные точки, а не обязательный список и не рейтинг.

| Задача | Возможный подход | Что изучить |
| --- | --- | --- |
| Интерфейс веб-приложения | React | [Официальное введение](https://react.dev/learn) |
| Веб-приложение на Python с данными на сервере | Django | [Руководство по основным возможностям](https://docs.djangoproject.com/en/6.0/topics/) |
| Android-приложение | Kotlin | [Материалы Android Developers](https://developer.android.com/kotlin/) |
| Игровой проект | Unity | [Официальное руководство](https://docs.unity3d.com/Manual/UnityManual.html) |

Можно использовать другие технологии. Важнее, чтобы команда понимала их роль и могла получить работающую сборку.

IDE, редактор изображений и система контроля версий — рабочие инструменты. В разделе стека на слайдах требуются технологии структурных частей самого проекта.

## Проверьте выбор на маленьком примере

Прежде чем окончательно выбрать технологию, попробуйте её в деле:

- создать пустой проект;
- реализовать одно простое действие;
- собрать приложение;
- открыть его на другом устройстве или разместить на выбранном хостинге;
- проверить доступ к необходимым данным.

Так обнаружатся риски, которые не видны из учебного видео: сложности сборки, недоступный сервис, неподдерживаемое устройство или отсутствие нужных данных.

## Где будет работать сервис

Если проект требует деплоя, выясните, где он будет работать в течение проверки. До выбора площадки проверьте доступность регистрации, условия оплаты, ограничения ресурсов и возможность сохранять данные.

Не рассчитывайте на бесплатный тариф или студенческую льготу, пока не проверили условия и фактический доступ команды.

Для сайта или онлайн-сервиса к GitHub-релизу прикладывается публичная ссылка. Проверяемый деплой после сдачи нельзя подменять.

## Как объяснить выбор в аннотации

Достаточно объяснить:

> Интерфейс — выбранная технология, потому что команда умеет создавать на ней нужные экраны. Сервер — выбранный фреймворк для работы с данными. Размещение — проверенная площадка, на которой уже запускается пробная версия.

Это пример логики обоснования. Не копируйте его без собственных проверок.
