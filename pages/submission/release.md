# Сборка, релиз и сдача

Сдать проект — значит передать жюри конкретную версию, которую можно открыть и проверить. Ссылка на репозиторий с исходниками сама по себе не заменяет сборку или работающий сервис.

## Термины

| Термин | Что означает |
| --- | --- |
| Исходники | Код и материалы, из которых создаётся приложение |
| Коммит | Зафиксированное состояние изменений в истории Git |
| Сборка, или билд | Версия программы, подготовленная для запуска |
| Деплой | Размещение работающей версии сервиса, например сайта |
| Тег | Метка версии в истории Git |
| Релиз | Страница выпуска в GitHub с тегом, описанием и файлами либо ссылкой для проверки |

GitHub может автоматически приложить к релизу архивы исходников. Это исходный код, а не готовая сборка приложения. О составе релиза см. [документацию GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

## Что сдаётся по типам проекта

| Проект | Материал для проверки |
| --- | --- |
| Игра или десктопное приложение | Один архив со сборкой |
| Android-приложение | Один APK-файл |
| Сайт или другой онлайн-сервис | Публичная ссылка на работающую версию в описании релиза |
| Проект из нескольких частей | Материалы и инструкции, позволяющие проверить его как целое |

Название архива или APK должно соответствовать названию проекта. Например, `CampusGuide-zero.zip` понятнее, чем `build.zip`, `pd.zip` или `app_release.apk`.

В корне архива может находиться установочная программа с названием проекта либо каталог со всеми файлами приложения, также названный по проекту. Не заставляйте проверяющего выбирать между несколькими папками «новое», «старое» и «точно финал».

## Как подготовить версию

1. Завершите работы, которые войдут в версию для сдачи.
2. Зафиксируйте соответствующий коммит.
3. Соберите приложение или разместите именно эту версию сервиса.
4. Проверьте её по инструкции на другом устройстве.
5. Подготовьте описание: что доступно, как запустить, что проверить и какие есть ограничения.

Для сайта или онлайн-сервиса проверьте доступность всех необходимых частей: интерфейса, сервера и данных. Адрес вида `localhost` открывается только на вашем компьютере — это не деплой.

## Как опубликовать релиз на GitHub

1. Откройте репозиторий и раздел **Releases**.
2. Выберите **Draft a new release**.
3. В поле **Choose a tag** введите имя нового тега, например `zero-version` или `v0.1`, и выберите **Create new tag on publish**. В поле **Target** укажите ветку или коммит, из которого сделана сборка. Если тег уже создан в Git, выберите его из списка и проверьте связанный с ним коммит.
4. Укажите понятное название этапа и версии, например «Нулевая версия».
5. Добавьте описание запуска, проверки и ограничений.
6. Прикрепите сборку либо укажите ссылку на деплой.
7. Опубликуйте релиз кнопкой **Publish release**.

Сохранённый черновик не равен опубликованному релизу. После публикации откройте страницу без входа в аккаунт владельца и проверьте скачивание или переход на сайт. Действия интерфейса описаны в [официальной инструкции GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).

Тег релиза должен указывать на тот коммит, из которого собран приложенный файл или сделан деплой, — а не на более свежий код, которого в сборке ещё нет.

## Сроки сдачи

На странице этапа в кабинете посмотрите **дедлайн билда**. По общему правилу версию передают не менее чем за неделю до начала защит этапа. Не путайте срок сдачи с датой собственного выступления.

Оставьте время на загрузку файлов и проверку ссылок. Создание репозитория, тега без релиза или черновика не заменяет публикацию проверяемой версии.

### Как кабинет определяет время сдачи

Временем сдачи считается **момент публикации релиза на GitHub** — не дата коммита, не создание тега и не сохранение черновика. Из этого следует несколько практических правил:

- **Для каждого этапа публикуйте новый релиз.** Релиз предыдущего этапа и релиз, опубликованный задолго до дедлайна (более чем за две недели), к текущему этапу не относится.
- **До дедлайна версию можно обновить новым релизом.** Если до дедлайна опубликовано несколько релизов, проверяется последний из них. Это не подмена: подменой считается изменение сданного после дедлайна.
- **Релиз после дедлайна — просрочка.** Штраф растёт с каждым часом опоздания, поэтому при опоздании публикуйте рабочую версию сразу, а не откладывайте до утра. Если релиза нет совсем, штраф максимальный.
- **Публикуйте релиз в репозитории, который сохранён в кабинете.** Релиз в другом репозитории, например в отдельном репозитории бэкенда, кабинет не увидит.

Если к дедлайну готово не всё, опубликуйте то, что запускается, и честно опишите в релизе, что не сделано: рабочая неидеальная версия в срок выгоднее опоздания.

Не планируйте публикацию на последние минуты: загрузка большого архива может занять больше времени, чем вы ожидаете.

## После сдачи версию нельзя подменять

**Сданный релиз нельзя подменять. Запрет распространяется и на деплой — сайт или сервис, который проверяет жюри.** За подмену может быть назначен штраф.

Не заменяйте архив или APK другим содержимым и не выкладывайте обновлённое приложение по той же проверяемой ссылке. Не переносите тег сданной версии на другой коммит. Жюри должно проверять одну и ту же сданную версию.

### Как продолжать разработку во время проверки

Работа над следующей версией не останавливается, но сданная версия должна оставаться нетронутой:

- не меняйте файлы опубликованного релиза и не переносите его тег;
- для сайта не выкладывайте новые изменения на проверяемый адрес. Если деплой срабатывает автоматически при каждом изменении основной ветки, на время проверки отключите его или разрабатывайте в отдельной ветке;
- описание репозитория и README исправлять можно, пока инструкция описывает именно сданную версию;
- если сервис упал, поднимите его в той же версии — это не подмена. Выкладывать исправленную версию нельзя.

Если обнаружена критическая ошибка, мешающая проверке, сообщите организатору и проверяющим: название команды, этап, ссылку на релиз, проявление ошибки и время обнаружения. Не считайте сообщение автоматическим разрешением подменить версию.

## Презентация сдаётся отдельно

У презентации свой дедлайн. Подготовьте PDF; если требуется анимация, допускается PPTX. Передайте ссылку через форму сбора презентаций текущего этапа, опубликованную организатором. Проверьте выбор команды и доступ по ссылке: файл должен открываться без входа в ваш аккаунт.

Если форму отправили повторно, учитываются последний вариант и время его отправки. Исправить слайды до дедлайна можно; при повторной отправке после дедлайна временем сдачи станет время новой отправки, то есть презентация окажется сданной позже срока.

Аннотация заполняется прямо в кабинете — порядок есть в [отдельной инструкции](../stages/annotation.md).

## Контрольный список

- [ ] В кабинете сохранён правильный репозиторий команды.
- [ ] Релиз опубликован и относится к нужному этапу.
- [ ] Файл или деплой соответствует указанному коммиту.
- [ ] Материалы открываются без доступа владельца.
- [ ] Запуск и короткий сценарий проверки описаны.
- [ ] Сборка проверена после скачивания, а не только из рабочей папки разработчика.
- [ ] Презентация сдана отдельно в свой срок.
- [ ] После сдачи проверяемая версия не подменяется.
