# Как выбрать технологии

Стек — набор технологий, из которых состоят части проекта. Единственно правильного стека нет: похожие задачи команды успешно решают на разных технологиях. На этой странице собраны варианты для каждой платформы, их отличия и вопросы, которые помогают выбрать.

Таблицы ниже — частые варианты, а не обязательный или рекомендованный список. Можно взять и другую технологию, если команда понимает её роль и сможет получить работающую сборку.

Главные ориентиры — что уже знает команда, где будет работать пользователь и как жюри запустит результат. Длинный список технологий сам по себе не делает проект сложнее или качественнее: если игре достаточно движка, сервер и база данных только ради списка не нужны.

## Порядок выбора

1. **Платформа.** Где пользователь будет работать: в браузере, на телефоне или на компьютере? От ответа зависит всё остальное.
2. **Интерфейс.** На чём сделать то, что видит пользователь. Варианты — в разделах по платформам ниже.
3. **Сервер.** Нужен ли он: пользуются ли несколько человек общими данными, или всё работает на устройстве пользователя?
4. **Данные.** Что нужно сохранять и где: в файле на устройстве или в базе данных на сервере.
5. **Проверка.** Как жюри откроет результат: по ссылке, установив сборку или запустив игру.

Прежде чем выбирать технологии, опишите части системы словами. Например: «Интерфейс показывает карту и поиск; сервер обрабатывает запросы; база данных хранит аудитории и переходы».

Дальше часто встречается слово **фреймворк** — готовый каркас приложения, в который команда добавляет свой код. Он берёт на себя типовые задачи: маршруты, работу с базой данных, отрисовку интерфейса.

## Веб-приложение

Веб-приложение открывается в браузере: жюри достаточно ссылки, а одна версия работает и на компьютере, и на телефоне. Обычно в нём две части: интерфейс в браузере (фронтенд) и сервер (бэкенд). Для проверки понадобится [деплой](#где-будет-работать-сервис).

Сначала решите, нужен ли сервер:

- **Пользователи работают с общими данными: записи, расписание, рейтинг** — нужны фронтенд на JavaScript-фреймворке и сервер, который хранит данные и отдаёт их через API.
- **Хранить общие данные не нужно: калькулятор, визуализация, справочник** — достаточно статического сайта без сервера.

Интерфейс:

| Технология | Язык | Особенности |
| --- | --- | --- |
| [React](https://react.dev/learn) | JavaScript или TypeScript | Самая большая экосистема библиотек и учебных материалов |
| [Vue](https://vuejs.org/guide/introduction.html) | JavaScript или TypeScript | Невысокий порог входа, шаблоны близки к обычному HTML |
| [Angular](https://angular.dev/overview) | TypeScript | Многое встроено сразу, строгая структура проекта; порог входа выше |
| [Svelte](https://svelte.dev/docs) | JavaScript или TypeScript | Мало шаблонного кода и небольшой размер сборки; экосистема меньше |

Сервер удобнее выбирать по языку, который команда уже знает:

| Язык | Фреймворки | Особенности |
| --- | --- | --- |
| Python | [Django](https://docs.djangoproject.com/en/stable/), [FastAPI](https://fastapi.tiangolo.com/tutorial/), [Flask](https://flask.palletsprojects.com/) | В Django многое встроено: авторизация, админка, работа с базой данных; FastAPI — лёгкий фреймворк для API с автоматической документацией; Flask минимален |
| C# | [ASP.NET Core](https://learn.microsoft.com/aspnet/core/) | Подробная документация и высокая производительность; привычен тем, кто пишет на C# |
| Java, Kotlin | [Spring Boot](https://spring.io/guides), [Ktor](https://ktor.io/docs/) | Spring Boot широко используется в индустрии, но требует настройки; Ktor легче и написан для Kotlin |
| JavaScript, TypeScript | [Express](https://expressjs.com/), [NestJS](https://docs.nestjs.com/) | Один язык с интерфейсом; NestJS задаёт структуру для большого проекта |
| Go | [стандартная библиотека](https://go.dev/doc/) | Простой язык; сервер собирается в один исполняемый файл, что упрощает деплой |

## Мобильное приложение

**Первый вопрос — нужен ли iOS.** С него начинается выбор, потому что у iOS два жёстких условия, и никакой фреймворк их не обходит:

- собрать приложение для iOS можно только на **Mac** в Xcode;
- чтобы жюри установило сборку на свой iPhone, нужен **платный аккаунт в Apple Developer Program**.

Если у команды нет хотя бы одного из них, делайте приложение для Android: его сборку (файл `.apk`) можно приложить к релизу, и жюри установит её напрямую.

Дальше выбор такой:

- **Только Android** — Kotlin и [Jetpack Compose](https://developer.android.com/compose). Это основной путь, который продвигает Google: официальные курсы, полный доступ к возможностям устройства. Java тоже поддерживается, но новые материалы Google выпускает для Kotlin.
- **Android и iOS, условия для iOS выполнены** — кроссплатформенная разработка: один код собирается под обе платформы.
  - [Flutter](https://docs.flutter.dev/) на языке Dart. Интерфейс выглядит одинаково на всех платформах, изменения видны почти сразу без полной пересборки. Dart придётся выучить, но он похож на Java и C#.
  - [Compose Multiplatform](https://www.jetbrains.com/compose-multiplatform/) на Kotlin. Интерфейс пишется так же, как в Jetpack Compose для Android, поэтому начать можно с Android и добавить iOS позже, не переписывая экраны. Подходит команде, которая знает Kotlin.

**Нативное** приложение пишется инструментами самой платформы: Kotlin для Android, Swift для iOS. Два нативных приложения — это два отдельных проекта и вдвое больше работы, поэтому для обеих платформ обычно выбирают кроссплатформенный вариант.

Требования к версиям Android и архитектурам процессора — на странице [«Тестирование и совместимость»](../submission/testing.md).

## Десктопное приложение

Жюри запускает десктопное приложение на своём компьютере, поэтому решите, на каких ОС оно должно работать.

- **Только Windows** — C# с [WinForms](https://learn.microsoft.com/dotnet/desktop/winforms/) или [WPF](https://learn.microsoft.com/dotnet/desktop/wpf/). WinForms проще в начале, WPF даёт больше свободы в оформлении.
- **Windows, macOS и Linux** — [Avalonia](https://docs.avaloniaui.net/) на C#, [JavaFX](https://openjfx.io/) на Java или Kotlin, [Qt for Python](https://doc.qt.io/qtforpython-6/) на Python.
- **Команда знает веб-технологии** — [Electron](https://www.electronjs.org/docs/latest): привычный стек, но сборка весит много. [Tauri](https://tauri.app/) даёт лёгкие сборки, но его ядро, которое работает с системой, пишется на Rust.
- **Небольшой инструмент на Python** — [Tkinter](https://docs.python.org/3/library/tkinter.html), который входит в стандартную поставку Python.

Приложите к релизу установщик или архив со всем необходимым. Для Python и Java это значит собрать исполняемый файл или подробно описать установку среды: проверяющий не должен догадываться, чего не хватает. Подробнее — в разделе о [десктопных приложениях](../submission/testing.md).

## Игра

Выбор движка зависит от трёх вопросов: 2D или 3D, где в игру будут играть и какой язык знает команда.

| Движок | Язык | Особенности |
| --- | --- | --- |
| [Unity](https://docs.unity3d.com/Manual/UnityManual.html) | C# | Много уроков и готовых ассетов; 2D и 3D; сборки для компьютера, Android и браузера |
| [Godot](https://docs.godotengine.org/) | GDScript, C# | Лёгкий, открытый и бесплатный; особенно удобен для 2D |
| [Unreal Engine](https://dev.epicgames.com/documentation/en-us/unreal-engine) | C++, Blueprints | Сильная 3D-графика, но нужен мощный компьютер, а порог входа высокий |
| [Phaser](https://docs.phaser.io/) | JavaScript, TypeScript | 2D-игры в браузере: жюри играет по ссылке без установки |
| [Pygame](https://www.pygame.org/docs/) | Python | Простые 2D-игры; сборку для запуска на другом компьютере придётся готовить отдельно |

Сборка для браузера — самый простой способ дать жюри поиграть: не нужно ничего устанавливать. Если игра рассчитана на компьютер, проверьте запуск на машине без установленного движка. Перед началом работы проверьте лицензию движка и готовых ассетов — см. [сторонние материалы](../submission/resources.md).

## Сервер и данные

Сервер нужен не только веб-приложению. Если мобильное или десктопное приложение работает с общими данными — например, у пользователей общее расписание или рейтинг, — выберите сервер из [таблицы выше](#веб-приложение).

Где хранить данные:

| Вариант | Когда подходит |
| --- | --- |
| Файлы на устройстве | Настройки и данные одного пользователя, которые не нужно видеть с других устройств |
| [SQLite](https://www.sqlite.org/docs.html) | Встроенная база данных в одном файле: для приложения на устройстве или небольшого сервера без отдельной службы |
| [PostgreSQL](https://www.postgresql.org/docs/current/tutorial.html) | Общие данные многих пользователей на сервере; самая распространённая открытая СУБД |
| MySQL, MariaDB | Похожая на PostgreSQL роль; часто есть на недорогом хостинге |
| MongoDB | Документы без строгой схемы; для связанных между собой данных реляционная база обычно проще |

Готовые облачные бэкенды, например Firebase или Supabase, избавляют от собственного сервера, но делают проект зависимым от внешнего сервиса. Заранее проверьте, что команда может в нём зарегистрироваться и пользоваться им, и укажите его в стеке.

## Проверка на маленьком примере

Прежде чем окончательно выбрать технологию, попробуйте её в деле:

- создайте пустой проект;
- реализуйте одно простое действие;
- соберите приложение;
- откройте его на другом устройстве или разместите на выбранном хостинге;
- проверьте доступ к нужным данным.

Так обнаружатся риски, которые не видны из учебного видео: сложности сборки, недоступный сервис, неподдерживаемое устройство или отсутствие нужных данных.

## Где будет работать сервис

Если проекту нужен деплой, выясните, где он будет работать во время проверки. До выбора площадки проверьте доступность регистрации, условия оплаты, ограничения ресурсов и возможность сохранять данные.

Не рассчитывайте на бесплатный тариф или студенческую льготу, пока не проверили условия и фактический доступ команды.

Для сайта или онлайн-сервиса к GitHub-релизу прикладывается публичная ссылка. Проверяемый деплой после сдачи нельзя подменять.

## Как объяснить выбор в аннотации

Достаточно объяснить:

> Интерфейс — выбранная технология, потому что команда умеет создавать на ней нужные экраны. Сервер — выбранный фреймворк для работы с данными. Размещение — проверенная площадка, на которой уже запускается пробная версия.

Это пример логики обоснования. Не копируйте его без собственных проверок.

IDE, редактор изображений и система контроля версий — рабочие инструменты, а не стек. В разделе стека на слайдах перечисляйте технологии частей самого проекта.
