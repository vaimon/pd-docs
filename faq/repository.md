## Какие требования к репозиторию?

Открытый репозиторий на GitHub, регулярные коммиты с содержательными сообщениями, задачи и ошибки — в issues. В README — идея, цель, задачи, части проекта и инструкция запуска. Версия для проверки публикуется в Releases. За запущенный репозиторий предусмотрен штраф. См. [репозиторий и README](../pages/submission/repository.md).

## Можно ли держать репозиторий закрытым до защиты?

Нет. Репозиторий открыт с самого начала: по нему жюри следит за ходом работы, а кабинет закрытый репозиторий просто не увидит и не даст сохранить ссылку. Пароли и ключи доступа в репозиторий не кладите. См. [как завести репозиторий](../pages/submission/repository.md).

## Кто должен быть владельцем репозитория?

Любой участник команды или созданная командой организация на GitHub — требований к владельцу нет. Важно, чтобы у всех участников был доступ на запись и чтобы ссылку на этот репозиторий тимлид сохранил в кабинете. См. [как завести репозиторий](../pages/submission/repository.md).

## README обязательно делать в Markdown?

Да, нужен файл `README.md`: GitHub показывает его как оформленное описание проекта. Учить разметку специально не придётся — хватит заголовков, списков и ссылок. Готовая структура — в [заготовке README](../pages/submission/repository.md).

## Нужно ли указывать Git и GitHub в стеке технологий?

Нет. Git — система контроля версий, GitHub — площадка для репозитория; IDE и графические редакторы тоже не стек. На слайде со стеком нужны технологии частей самого приложения: интерфейса, сервера, базы данных. Ссылка на репозиторий указывается отдельно. См. [как выбрать технологии](../pages/extra/stack-ideas.md).

## Почему кабинет не видит мои коммиты?

Причин обычно три: не указан GitHub-логин в кабинете; почта, записанная в коммитах, не добавлена в ваш аккаунт GitHub; коммиты лежат в отдельной ветке и не влиты в ветку по умолчанию. Ещё статистика обновляется не мгновенно — посмотрите на дату рядом с цифрами. Непривязанные коммиты не доказывают, что вы не работали, но исправить привязку стоит. См. [как проверить, что коммиты привязаны к вам](../pages/common-info/team.md).

## Почему участника нет на графике Contributors?

По тем же причинам: график GitHub считает только коммиты в ветке по умолчанию и только те, чья почта связана с аккаунтом. Подробнее — в [справке GitHub](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/viewing-a-projects-contributors). Не вливайте изменения в сданную версию ради графика: объясните ситуацию проверяющему.

## Как дизайнеру показать работу в Figma?

Добавьте в README ссылку на файл Figma с доступом для просмотра и напишите, что именно сделано. Готовые ресурсы, которые вошли в проект, — иконки, иллюстрации — всё равно загрузите в репозиторий от своего имени. См. [работа вне Git](../pages/submission/repository.md).

## Можно ли держать бэкенд в отдельном репозитории?

Нет. Весь проект ведётся в одном репозитории: клиент, сервер и другие части лежат в отдельных папках, например `frontend/` и `backend/`. Подключать части через Git submodules тоже не нужно. Кабинет видит релизы и считает статистику коммитов только по одному репозиторию. См. [один репозиторий на проект](../pages/submission/repository.md).

## Куда класть большие файлы: сборки и тяжёлые ассеты?

Сборку прикладывайте к релизу, а не добавляйте в репозиторий коммитом. GitHub не принимает в репозиторий файлы больше 100 МБ; для крупных ассетов игры используйте Git LFS или храните исходники отдельно, оставив в репозитории то, что нужно для сборки. См. [сборка, релиз и сдача](../pages/submission/release.md).
