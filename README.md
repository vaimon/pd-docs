# Руководство участника ПД ФИИТ

Этот репозиторий — источник документации, которую личный кабинет ПД отображает в собственном интерфейсе. Содержимое хранится как переносимый Markdown-bundle и не требует Sphinx или GitHub Pages.

Студенту: начните со страницы [«С чего начать»](pages/overview.md).

## Разделы руководства

| Раздел | Содержание |
| --- | --- |
| Начать работу | Устройство курса, формирование команды, личный кабинет |
| Пройти этапы | Аннотация и отдельная инструкция каждого этапа |
| Подготовить и сдать | Требования, репозиторий, релиз, слайды, тестирование, ресурсы |
| Разобраться в результатах | Оценки, штрафы, обратная связь |
| Примеры и помощь | Выбор технологий, словарь терминов |

## Редакторские правила

- Пишите для студентов 1–2 курсов ФИИТ; объясняйте термины при первом использовании.
- Разделяйте обязательные требования, рекомендации и учебные примеры.
- Правила курса подтверждаются организатором. Возможность в коде не вводит новую обязанность студента.
- Университетские пороги зачёта и оценок: 60 баллов для зачёта и «удовлетворительно», 71 для «хорошо», 85 для «отлично». Таблица находится на странице [«Оценивание»](pages/results/grading.md), FAQ даёт короткий ответ со ссылкой на неё.
- Страницы `pages/` не могут ссылаться на файлы `faq/`: валидатор и кабинет разрешают внутренние ссылки только на страницы из manifest. Ссылки из FAQ на страницы разрешены.
- Регламент выступления на всех этапах — от 4 до 6 минут включительно. За выступление короче 4 или дольше 6 минут предусмотрен штраф; пять минут — удобная цель для репетиции.
- Используйте термин «тимлид» во всём руководстве, в том числе при описании экранов.
- Для проекта требуются Git и открытый репозиторий на GitHub.
- Максимум за этапы — 100 баллов; на итоговой защите присуждаются до 10 дополнительных баллов за номинации. Общий максимум — 110.
- Стандартный состав команды — шесть человек: три с первого курса и три со второго. Исключения согласуются с организатором; после фиксации состава изменения возможны только по форс-мажору через организатора.
- Пересдачи этапов нет: после публикации баллы этапа фиксируются. Разбор несогласия с оценкой — отдельная процедура, не пересдача.
- Штрафы описываются принципами, без ставок и формул: они настраиваются в системе и могут меняться. Допустимо называть предел — сумма штрафов за этап не превышает трети его максимума.
- Календарь года даётся как ориентир по прошлым сезонам; точные даты — только в кабинете и объявлениях.
- ИИ-инструменты разрешены; за результат отвечает команда, каждый участник объясняет свою часть, сгенерированные материалы указываются как сторонние.
- Объявления организатора публикуются в Telegram-чате ПД. Ссылку на чат в репозиторий не добавляйте: он публичный.
- Новые термины добавляйте в [словарь](pages/extra/glossary.md) и объясняйте при первом использовании на странице. Не придумывайте собственных терминов: берите слова, которые студент видит в кабинете или слышит от жюри.
- Единый словарь: «итоговая защита» (не «финал», не «финальная защита»); «сессия» (не «собрание»); «сервис подбора команд» (не `team-selection` и не «портал»); «десктопное приложение» (не «настольное»); «деплой» (не «веб-деплой», не «размещённый сервис»); «сданная версия» (не «сдаваемая», «переданная», «сдававшаяся»); «проверяющие» (не «проверявшее жюри»); «штрафы» (не «санкции»); «возможности» (не «функционал»); «список сторонних материалов» (не «реестр»). Слово «сессия» не используйте в значении «вход в аккаунт».
- Заголовок первого уровня страницы совпадает с её `title` в `manifest.json`. Заголовки разделов — существительное или вопрос «Как…»; инфинитивы допустимы только в пошаговых инструкциях (кабинет, сервис подбора команд).
- Пишите простыми предложениями в действительном залоге. Избегайте канцелярита: «не является», «в полной мере», «осуществляется», «обработать замечание», «на данный момент».
- FAQ даёт короткий ответ и ссылку на подробную страницу; не создавайте в нём отдельный регламент.
- Сохраняйте существующие slug при переименовании и переносе страниц. Удалённые по решению организатора страницы и ссылки на них не восстанавливайте.
- Перед изменением инструкции кабинета проверяйте действующие маршруты и экраны приложения, а не только имена сохранившихся компонентов.
- Не обещайте исключений из запрета подмены сданного релиза и деплоя без подтверждённого решения организатора.

## Структура

- `manifest.json` задаёт заголовок, разделы, порядок страниц и стабильные URL-slug.
- `pages/` содержит страницы в формате GitHub Flavored Markdown.
- `faq/` содержит ответы на частые вопросы, сгруппированные по разделам из `manifest.json`. Вопрос формулируется так, как его задал бы студент, и лежит в том разделе, где студент станет его искать; один вопрос — в одном разделе.
- `assets/` предназначен только для локальных raster-изображений документации.
- `scripts/validate.mjs` проверяет контракт bundle перед публикацией.

Имена slug, файлов и расширений используют строчные латинские буквы, цифры и дефисы. В Markdown разрешены обычные и внутренние ссылки, но не raw HTML, внешние изображения, symlink или пути за пределами bundle. Локальные изображения хранятся в `assets/`; разрешены расширения `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp` и `.avif` только в нижнем регистре. SVG не допускается как активный same-origin контент.

### Формат FAQ

Блок `faq` в `manifest.json` задаёт общий заголовок и упорядоченный список разделов с `slug`, `title` и путём `file`. Для каждого раздела используется отдельный файл `faq/*.md`.

Каждый вопрос начинается заголовком второго уровня `##`, а ответ продолжается до следующего такого заголовка:

```markdown
## Как сдать проект?

Ответ может содержать **Markdown**, списки, безопасные ссылки и код.
```

Заголовок первого уровня запрещён. Вопрос и ответ не могут быть пустыми; заголовки `###` и ниже допустимы внутри ответа. Валидатор также запрещает raw HTML, небезопасные ссылки, внешние изображения, symlink и FAQ-файлы, не перечисленные в manifest.

## Изменение документации

1. Создайте ветку от `main`.
2. Измените Markdown и при необходимости `manifest.json`.
3. Выполните:

   ```bash
   npm test
   npm run validate
   ```

4. Откройте pull request и после проверки объедините его в `main`.

## Публикация

После merge администратор приложения публикует точный коммит:

```bash
./deploy.sh docs <full-commit-sha>
```

Приложение хранит каждый опубликованный commit как неизменяемый релиз. Повторная публикация предыдущего SHA выполняет откат без пересборки приложения.
