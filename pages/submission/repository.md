# Репозиторий и README

Репозиторий хранит исходники, материалы и историю разработки. По нему жюри изучает проект и вклад участников, оставляет замечания и находит сданные версии.

## Как завести репозиторий

Используйте Git и создайте открытый репозиторий проекта на **GitHub**. Организуйте доступ участников к работе с ним. Тимлид должен сохранить ссылку в разделе «Моя команда» в кабинете.

Сейчас для ПД подходит только **GitHub**: с ним связаны репозиторий в кабинете, история коммитов и публикация сборок через GitHub Releases.

Владельцем репозитория может быть любой участник или созданная командой организация на GitHub. Репозиторий открыт с самого начала работы, а не только к защите: по нему жюри следит за ходом проекта.

Проверьте ссылку без входа в аккаунт владельца: исходники, README и опубликованная версия должны быть доступны проверяющим.

## Понятная история коммитов

Коммит — отдельное сохранённое изменение проекта. Сообщение должно объяснять его смысл. Например:

| Неинформативно | Понятнее |
| --- | --- |
| `fix` | `Исправить поиск аудитории с пробелами в запросе` |
| `update` | `Добавить экран результатов поиска` |
| `final` | `Обновить инструкцию запуска для нулевой версии` |

Одна из возможных конвенций сообщений — [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Обязательное требование курса — содержательные сообщения; конкретный стиль команда выбирает так, чтобы история оставалась понятной.

Работу тестировщиков ведите через issues. Дизайнеры, музыканты и другие участники загружают созданные ресурсы в репозиторий. Как показывать результат каждого — на странице [«Команда и вклад»](../common-info/team.md).

## Большие файлы

Сборку прикладывайте к релизу, а не добавляйте в репозиторий коммитом. GitHub не принимает в репозиторий файлы больше 100 МБ. Для крупных ассетов игры используйте Git LFS или храните их исходники отдельно, оставив в репозитории то, что нужно для сборки.

## Несколько репозиториев

Если у проекта несколько репозиториев — например, отдельные для клиента и сервера, — открытыми должны быть все. В кабинете сохраняется один, основной: в нём публикуются релизы этапов, а в его README стоят ссылки на остальные репозитории и объяснение, как части связаны. Учтите, что кабинет считает статистику коммитов только по основному репозиторию: о работе в других расскажите на слайдах о вкладе.

## Работа вне Git

Дизайнер, который работает в Figma, добавляет в README ссылку на файл с открытым доступом для просмотра. Готовые ресурсы, которые вошли в проект, — иконки, иллюстрации, звуки — всё равно загружаются в репозиторий от имени автора: так вклад виден в истории.

## Что написать в README

README — первая инструкция для человека, который открыл проект. В нём должны быть:

1. **Идея:** что вы создаёте и для кого.
2. **Тип проекта:** сайт, приложение, игра, чат-бот или другой вариант.
3. **Цель и задачи:** какой результат хотите получить и какие работы для этого нужны.
4. **Структурные части и технологии:** например, база данных, сервер и интерфейс.
5. **Запуск и проверка:** как открыть проект, что нужно установить, какие действия выполнить.
6. **Подсказки для жюри:** тестовые сценарии и, для игры, читы или режим проверки.

IDE, система контроля версий и графические редакторы не относятся к стеку частей приложения. Перечисляйте технологии в связи с их назначением: «База данных — PostgreSQL; сервер — ASP.NET Core; интерфейс — React».

## Рекомендуемая заготовка README

Ниже структура, которую можно адаптировать. Замените пояснения реальными сведениями о проекте.

```markdown
# Название проекта

## Идея и аудитория
Какую задачу решает проект и кто им пользуется.

## Цель и задачи
Какой результат должен получиться и что нужно для его достижения.

## Тип и части проекта
Тип продукта. Части системы и технологии каждой части.

## Версия для проверки
Ссылка на релиз и, если нужен, работающий деплой.

## Как запустить
Поддерживаемая платформа, зависимости и последовательность действий.

## Как проверить
Короткий основной сценарий. Тестовые данные, подсказки и читы.

## Возможности и ограничения
Что доступно в этой версии, какие особенности нужно знать.

## Сторонние материалы
Ссылка на LICENSE.md.
```

README должен соответствовать сданной версии. Если инструкция описывает ещё не выпущенную функцию, проверяющий не сможет понять, где ошибка: в программе или в описании.

## Как отвечать на issues

На замечания жюри нужно отвечать и разбираться с ними до следующего этапа. После исправления желательно открыть pull request и по возможности пригласить автора issue к проверке. Минимум — ответить в комментариях и указать коммит, исправляющий проблему.

Пример содержательного ответа: «Исправили обработку пустого запроса в коммите … . Проверили пустую строку и строку из пробелов; сообщение об ошибке отображается».

Не публикуйте секреты в исходниках, README или примерах конфигурации. Доступность проекта для проверки обеспечивается рабочей сборкой и тестовым сценарием.
